# 0019. 支払日の表に確かめていない入金を数えない場合を並べ、見通しを計算し直せなかったときは「前の条件での計算」と示す

- 状態: 採用
- 日付: 2026-11-07
- 関連: #77、[ADR 0016](0016-pay-day-story-display-and-example.md)（支払日の表）、[ADR 0018](0018-reject-unverified-numbers-and-rank-by-effect.md)（照らせない額を採用しない）

## 背景

main 全体を Codex で点検したところ、次の 2 つが見つかった。どちらも、古い額や入るか分からない入金を、今の手元のお金の答えとして見せてしまう。

1. **支払日の表が、確かめていない入金を数えた額しか出さない。** CLAUDE.md は「確かめていない入金を手元のお金として数えない場合も並べる」と決めている。計算（`lib/money/ledger.ts`）は `high_case_without_unconfirmed_income` を出していて、詳しい表には出ていたが、見通しの先頭の支払日の表（ADR 0016）には出ていなかった。手元 0 円、11/8 に確かめていない給付金 100,000 円、11/10 に確かめた支払い 100,000 円のとき、表は「要る額 0 円・0 円残る・確かめた額」になり、給付金が入らない場合に要る 100,000 円が見えなかった。確かさの列も支払いの行だけで決めていて、数えた入金が仮定であることが出なかった。
2. **見通しを計算し直せないと、新しい内訳と古い要る額が混ざる。** `lib/money/attach.ts` は、その回に呼ばなかった道具の前回の結果を表に残す。総額を 80 万円から 160 万円に変え、新しい `kougaku_gendo` が成功したあと `simulate_cashflow` の前に時間切れになると（`lib/chat.ts` の時間切れの経路）、保険診療分は新しい 98,940 円、要る額は古い 115,690 円のまま並んだ（正しくは 123,690 円）。

## 決めたこと

1. **確かめていない入金がある筋書きは、支払日の表のすぐ下に「（筋書きの名前）・確かめていない入金を数えない場合」の行を足す。** 要る額・いつ・手元のお金との差は `high_case_without_unconfirmed_income` から出す。表の行は `lib/money/format.ts` の `paydayTable` が作り、画面はそれを並べるだけにする（画面で新しい額を作らない）。ただし、数えない場合の要る額といつが多めの場合と同じとき（入金が支払日より後で、要る額に効かないとき）は行を足さない。手元のお金との差も要る額から決まるので同じになり、同じ額の行が重なって見えるだけになるため（統括の判断、PR #80。体験例の 1 回目で、Claude が高額療養費の払い戻しを退院日より後の確かめていない入金として置くと、ほぼ毎回起きる）。その場合も、お金の出入りの表には「多めの場合で、確かめていない入金を数えない」の列が残る。
2. **確かさの列は、支払いと、その行で数えた入金の両方から決める。** 少なめの場合と多めの場合の両方の行を合わせる（入金に幅があると、少なめの場合だけが入金を数えていることがあるため。Codex の指摘・中 3）。0 円で数えた入金は額を動かさないので入れない。入金を数えない行の確かさは、その行で数えたものだけから決める。
3. **その回に内訳（`kougaku_gendo`・`meal_cost`）の計算が成功したあと、`simulate_cashflow` が無いか失敗したときは、残っている見通しに「前の条件での計算」の印（`stale_cashflow`）を付ける。** 判定は、その回の道具の呼び出しの順（`events`）だけで行う（`cashflowIsStale`）。日付だけの計算（`calc_date`）では印を付けない。日付の確かめだけで、額の見通しまで古いと示すのは過剰なため。
4. **印は前の回から引き継ぎ、見通しの計算し直しが成功した回でだけ外す**（Codex の指摘・高 1）。その回に内訳も見通しも成功しなければ（日付だけの計算や、文章の生成の失敗を含む）、前の印をそのまま残す。そのため、印はリクエストにも載せてサーバーへ送る（`moneyRequestSchema`）。カードを付け直さない回でも、印が外れていなければ、計算し直すよう頼む一文を出し続ける。
5. **印の付いた見通しは、今の額の照合の根拠にしない**（Codex の指摘・高 2）。返答の照合（サーバーが前の計算をやり直した結果）と、持ち出しの照合（`verifiedForExport`）の両方で外す。表には残す。印の付いたカードがあれば、持ち出しの文の先頭に注記を入れる（連絡のカードだけを持ち出すときも）。
6. **印があるあいだは、古い順位から質問文を作らない**（Codex の指摘・中 4）。「質問文をコピー」と「質問文を作ってもらう」を出さず、「計算し直すように頼む」（会話の入力欄に下書きを入れる。送るのは本人）を次の行動として出す。
7. **印が付いたときは、古い額を今の答えとして見せない。**
   - 見通しの先頭に注記を置き、支払日の表・まず確かめる 1 つ・お金の出入りの表の見出しに「（前の条件での計算）」を添える
   - 返答の下のリンクに要る額を書かない（`needRangeOf` が null を返す）
   - 持ち出しの文の先頭にも同じ注記を入れる
   - 返答の下の「確かめてほしいこと」に、「計算し直して」と送るよう頼む一文を出す
8. **触らないもの。** 返答の文の検査（`lib/money/guard.ts`）と `lib/chat.ts` の `softenClaims` は、別の作業が直しているので変えない。時間切れの経路は今のまま `attachMoney` を通るので、`chat.ts` は変えない。

## 検討したほかの案

| 案 | 採らなかった理由 |
| --- | --- |
| 確かめていない入金を数えない額だけを支払日の表に出す | 給付金が確かめた入金になったときとの比べができない。CLAUDE.md は両方を並べると決めている |
| 古い見通しを表から消す | 何を計算し直せばよいかの手がかりと、前の条件の額との比べが消える。注記つきで残し、計算し直すよう頼むほうが確か |
| 時間切れのとき、サーバーが自分で `simulate_cashflow` を呼び直す | 前の筋書きの入出金のどれを新しい内訳に差し替えるかを、プログラムが推測することになる。筋書きは会話で決めるもので、提出の前夜に足す変更として大きい |
| 印を付ける判定に `calc_date` も含める | 日付を確かめただけの回でも、額の見通しが古いと示すことになる |
| 確かめていない入金がある筋書きには、要る額が同じでも必ず行を足す | 入金が支払日より後のときは多めの場合と同じ額・同じ日の行が並び、何が違うのか読めない。体験例の 1 回目で、ほぼ毎回起きる |

## 結果

良くなること:

- 確かめていない給付金を当てにした額と、当てにしない額が、先頭の表で並ぶ
- 計算し直しが途中で止まっても、古い要る額が今の答えとして表・リンク・持ち出しに出ない

引き受けること:

- 確かめていない入金がある筋書きでは、支払日の表の行が増える
- 印は「その回の呼び出しの順」だけで決めるので、Claude が `simulate_cashflow` を呼ばずに内訳だけを計算し直した回でも付く（時間切れでなくても、古い額を今の額として見せないほうを選ぶ）

確かめ方: `tests/payday-and-stale.test.ts` に、背景の 2 つの再現の入力をそのまま置いた。直す前に、支払日の表の 2 件と、印の 2 件が赤になることを確かめた。
Codex の指摘（高 2・中 2）の再現は `tests/stale-carryover.test.ts`（印の引き継ぎ、返答と持ち出しの照合、入金に幅があるときの確かさ）と `e2e/payday-stale.test.ts`（印があるあいだの質問文）に置き、直す前に 5 件が赤になることを確かめた。

## 2026-11-08 追記（#97）

実 API の評価（[docs/validation/live-eval-20261108.md](../validation/live-eval-20261108.md)）で、Claude が `simulate_cashflow` のあとに同じ入力の `kougaku_gendo` をもう一度呼び、条件は変わっていないのに印が付く回が 31 回中 2 回あった。同じ回の前の内訳と同じ入力の内訳は、条件を変えないので数えないことにした。違う入力の内訳が見通しのあとにあれば、今までどおり印を付ける。

そのあと、直した版でデモと同じ 3 往復を通すと、3 回目で Claude が見通しのあとに「12 月に 80 万円」の内訳を呼び、印が付いた（前の回と同じ入力で、窓口負担 90,940 円は見通しの入出金にすでに入っていた）。見通しのあとの内訳でも、その額（食事代は保険診療分との合計も）が見通しの入出金に入っていれば数えないことにした。直したあと、デモ・月をまたぐ入院・入院日数を聞く・日付の変更を 3 回ずつ（21 回）通し、印は 0 回だった。
