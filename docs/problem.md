## 2. 子育て案の2つの場面

### A1. 復職前に、病気の日の預け先の準備を終える

**開く場面:** 1歳の子の親が12/1の復職前に、「急な発熱の朝、誰に預けられるのか」を確かめる。テオテのアカウントはあるが、子どもの施設登録が済んでいるか分からない。

**アプリでの流れ:**

1. 復職日と「アカウントあり／施設登録は未確認」を入れる。
2. 「次は利用したい施設への子どもの登録」と表示し、公式の施設検索へ進める。
3. 外部で登録後、親が登録状況を記録する。リンクを開いただけでは「済み」にしない。
4. 発熱した日は、医師の利用連絡書・予約開始時刻・利用可否の確認という残る手順を見られる。受入可否をアプリが判定しない。

**画面の一番上:**「復職前の準備：施設登録が未確認。アカウント作成とは別の手続きです」。11/16に確認する予定を本人が置いた例とする。この日は行政の締切ではない。

**変わること:** 準備の抜けを見つけ、公式サービスで登録まで進む。通常料金は利用料3,000円＋給食費など300円。減免や医師の文書費等は別。休まずに済む日数や節約額は算出できない。[札幌市の利用案内](https://kosodate.city.sapporo.jp/nenrei/mosugu/azukeru/1140.html)

**十分でない場合:** 本当に欲しいのが当日の空きの確保、送迎、病気の子を預ける不安への対応なら、この案では解決しない。テオテ自体で登録・予約ができるため、追加アプリに記録する手間に見合うかも未検証。

### A2. 出生後の申請で、1か月分の児童手当を受けそびれない

**開く場面:** 10/28に第1子が生まれた札幌市民の親。出生届は提出したが、児童手当の認定請求は未提出。公務員ではなく、通常の受給条件を満たす例。

**アプリでの流れ:** 生年月日と申請状況から、11/12（木）を15日特例の期限として示す。公式の申請案内と必要書類を開ける。提出後、親が「提出した日」を記録し、認定・初回振込は確認待ちとして残す。

| 親が行うこと                    | 支給対象になる月 | この例の差                     |
| ------------------------------- | ---------------- | ------------------------------ |
| 11/12までに認定請求             | 11月分から       | 11月分15,000円の受給につながる |
| 11/13に認定請求（例外事情なし） | 原則12月分から   | 11月分15,000円を受けられない   |

期限は10/28の翌日から15日目。3歳未満の第1子は月15,000円。新規申請時は通常の支給日と異なる場合があり、初回振込日を自動で確約しない。[札幌市の児童手当](https://kosodate.city.sapporo.jp/mokuteki/money/kodomo/1124.html)

**十分でない場合:** 窓口ですでに案内され申請も済んでいる家庭には、この場面での追加価値はない。金額は明確でも、繰り返し月額料金を払う理由には直結しない。

## 3. 入院案の2つの場面

### B1. 退院時に必要な現金を、入院前に確かめる

**開く場面:** 11/9〜16に予定入院する人が、病院の見積もりと口座を見比べる。後で返金されることは知っているが、退院時にいくら払うかは未確認。

**この例の前提:** 70歳未満・協会けんぽ・標準報酬月額28〜50万円の区分ウ。単月・1医療機関の入院で、保険診療の総医療費（10割）100万円、窓口負担割合3割。多数回該当、年間上限到達、他の診療との合算なし。対象外費用5万円と、この支払い用の手元資金30万円は架空の入力値。生活費等は手元資金から別に取り置いたとする。

2026年11月診療分に用いる上限は `85,800 + (1,000,000 − 286,000) × 1% = 92,940円`。[協会けんぽ・令和8年8月〜令和9年7月の表](https://www.kyoukaikenpo.or.jp/benefit/high_cost_medical_expenses/002/index.html)

| 11/16の支払い      | 窓口で上限を適用できず、後日還付 |  窓口で上限を適用 |
| ------------------ | -------------------------------: | ----------------: |
| 保険診療分         |                        300,000円 |          92,940円 |
| 対象外費用（仮定） |                         50,000円 |          50,000円 |
| その日に要るお金   |                    **350,000円** |     **142,940円** |
| 手元30万円との比較 |                 **50,000円不足** | **157,060円残る** |

**アプリでの流れ:**

1. 見積もり、診療月、区分、窓口での上限適用状況を入れる。区分が不明なら金額を確定せず、保険者への確認を先に示す。
2. 上の2通りを表示し、「病院に確認：今回の会計で上限が適用されますか」と確認文を出す。
3. マイナ保険証等で適用できるか、認定証が必要かを窓口に確認し、回答と確認日を記録する。既に適用が確認できていれば不要な申請を出さない。[協会けんぽ・利用方法](https://www.kyoukaikenpo.or.jp/benefit/high_cost_medical_expenses/001/index.html)
4. 病院の回答後、退院日の準備額を更新する。未確認の給付金は準備できたお金に含めない。

**変わること:** この条件では立替額が207,060円小さくなる。最終的な医療費の節約ではない。事後還付は協会けんぽの案内で診療月から3か月以上かかるため、退院日には使えない。確定した入金日も出さない。[協会けんぽFAQ](https://www.kyoukaikenpo.or.jp/faq/benefit/004/index.html)

**十分でない場合:** 病院が既に上限適用と見積もりを説明し、資金にも余裕がある人には、この確認だけの価値は小さい。支払い不足が分かってもアプリが現金を用意することはできない。

### B2. 「給付金は出るはず」を、書類の段取りと入金までの見通しに変える

**開く場面:** 11/16に退院する予定で、保険会社から診断書が必要と言われた人。12/10に15万円の支払いがある。既存の支出を引いた手元資金は12万円、請求を予定する給付金20万円は未入金。これはB1とは別の架空の家計。

**アプリでの流れ:**

1. 契約ごとに、請求する給付・受取人・必要書類・未確認事項を分ける。
2. まず保険会社に、診断書の要否と所定様式を確認する。必要な場合に、病院へ依頼可能日・作成目安を確認する。[必要書類が給付の種類で異なる例：アフラック](https://www.aflac.co.jp/keiyaku/seikyu/contents/insurance_claim.html)
3. 「必要書類が確定 → 診断書を依頼 → 書類を受け取る → 保険会社が受領 → 入金」を、次に進める条件とともに表示する。
4. 日程が延びたら、12/10の不足額を再表示する。未確定の入金を除いた場合は3万円不足と、先に分かる。

**日付を動かした比較:** 以下は期間の置き方を説明する例で、保険会社の支払約束や本人の予定ではない。病院作成を約2週間、郵送を1日、書類不備・追加調査なしと仮定。診断書が11/16に依頼可能であることも仮定した。

| 段階                            | 退院日に依頼できた場合   | 2週間あとに依頼した場合 |
| ------------------------------- | ------------------------ | ----------------------- |
| 診断書を依頼                    | 11/16                    | 11/30                   |
| 完成（約2週間を置いた試算）     | 11/30                    | 12/14                   |
| 保険会社に到着（仮定）          | 12/1                     | 12/15                   |
| 翌日から5営業日目の送金（仮定） | 12/8                     | 12/22                   |
| 翌銀行営業日の着金（仮定）      | 12/9                     | 12/23                   |
| 12/10の15万円の支払い直後       | 20万円が入れば17万円残る | 3万円不足               |

約2週間は[鳥取県立中央病院の公表例](https://www.pref.tottori.lg.jp/280887.htm)。到着翌日から5営業日以内の支払い・翌銀行営業日の円口座への着金は[メットライフ生命の公表例](https://faq.metlife.co.jp/answer/675187615a7cb3a9ba2b8571/)。異なる機関の例を組み合わせた仮定であり、ほかの病院・契約には流用しない。実装では利用者が確認した条件に置き換え、時期は見込みと確定を分ける。表中の営業日区間に土日以外の日本の祝日はない（[内閣府・2026年の祝日](https://www8.cao.go.jp/chosei/shukujitsu/gaiyou.html)）。

**変わること:** 追加の給付を作るのではなく、依頼し忘れによる遅れを減らし、入金が遅い場合の不足を支払日前に見つける。上の14日差・3万円不足は仮定からの計算結果であり、製品の実測効果ではない。

**十分でない場合:** 必要書類が分かっても依頼や請求を進める余力がなく、代行を必要としている人には足りない。診断・給付の可否・病理結果の時期はアプリが決められない。「がん給付は必ず術後」「短期入院なら必ず診断書不要」とも扱わない。

## 4. 原因についての仮説と、既存の方法との差

|                    | 子育て案                                               | 入院案                                                                           |
| ------------------ | ------------------------------------------------------ | -------------------------------------------------------------------------------- |
| 狙う人             | 出生・復職などが近く、未提出・未登録がある親           | 入院日や支払日が近く、書類と入出金の見通しが未確認の人                           |
| 原因の仮説         | 制度を知っていても、家庭に必要な準備が完了していない   | 窓口ごとの回答を、本人の書類の進み具合・支払日と結びつけられていない             |
| 既に手段を持つ相手 | 自治体窓口とテオテ。登録・予約の本体を担う             | 病院の会計・相談窓口、保険者、民間保険会社。制度・見積もり・請求条件を確認できる |
| アプリに残る役割   | 準備の抜けを見つけ、公式の手続きへ進み、完了を記録する | 各窓口への確認事項を出し、回答から次の作業と必要資金を更新する                   |
| 比べる相手         | 公式案内とカレンダーで済むか                           | 窓口への相談と手元のメモ・表で済むか                                             |
| 効果の確認         | 情報を読んだだけでなく、未完の申請・登録が進むか       | 日付と準備額に関わる未確認事項が解消し、依頼・請求が進むか                       |

「原因を誰も理解していない」とは確認できていない。各窓口には専門知識がある。製品の仮説は、それらを利用者の具体的な段取りへ結びつけることに追加価値がある、というもの。

通常のチャットや表に対しては、前提・出典・確認日を残し、未確認を勝手に補わず、予定の変更を後続の作業・残高へ反映する点を検証する。それでも既存の方法で十分なら、新しいアプリを作る根拠は弱い。

## 5. この段階の提案

**優先して検証するならB1・B2を一続きにした案。** 第一声は「退院日に必要なお金と、給付金が入るまでにすることを確かめる」。確認が進んだ結果を、日付と金額で比較しやすいから。ただし、強い困りごとがあることと、このアプリが欲しいことは別で、採用は未決定。

この案でも最初から税、事業継続、すべての保険商品まで広げる必要はない。まずは予定入院1件・月単位の支払い・民間保険1契約・書類の依頼と受領の流れを具体化する。必要なのは入出金額と日付、確定／見込み／未確認の区別であり、現在の子育て仕様の「公的な定額だけ」からは変更が必要になる。

月30ドルの支払意思は確認していない。入院という出来事を契機に使う案は、継続課金より1回の利用価値から検討するほうが自然という仮説にとどめる。節約・立替・給付時期の数字を料金の根拠に読み替えない。

その後、作者はB1・B2の優先検証を承認し、「金額や制度を利用する頻度をシミュレーションできれば、事前の準備に動けるのではないか」という仮説を示した。続けて、固定項目に入力するUIを明確に否定した。ADR 0007と検証仕様は、[会話からLLMが試算を組み立てる体験](validation/hospital-conversation.md)に改めた。入力式の[試作](prototypes/hospital-preparation.html)は内部計算の確認用に残す。理解、準備の意向、実際の行動変化を分けて確かめる。

## 6. 前回の評価から修正する点

- 「この形では使わない」は、その試作への回答。「無料でもどんな形でも使わない」への拡張はしない。
- 親の欠勤割合だけから「登録より欠勤を選んでいる」と原因を決めない。
- 現在のADR 0005には、作者の見通し表示への提案と、第2子の予定を入れる選択が記録されている。「見せ場だけのために追加された」とは言えない。
- 札幌市は初回予約時のアカウント作成も可能としている。「困った日には必ず間に合わない」は強すぎる。施設登録・医師の連絡書・空きの有無をそれぞれ確かめる必要がある。
- 入院の題材なら日付計算をそのまま持ち越せる、とは限らない。診療月、書類の前提関係、営業日、未確定の入金、残高計算を追加する必要がある。
- 仕様第4版・ADR 0004〜0006はこの作業ツリーに存在する。前回冒頭の「別の枝にしかない」は、現在の状態ではない。
