# 会話による入院前のシミュレーションから準備へ進むか：検証仕様

- [会話の体験案](hospital-conversation.md)／[内部計算の確認用](../prototypes/hospital-preparation.html)／[前段の4場面比較](../problem.md)
- 状態: 固定項目への入力式UIは作者の指摘で不採用。会話の体験を検証する。行動変化・支払意思は未確認

## 検証する課題

**先の出来事が、自分に必要な金額・回数・準備期限として具体化されていないため、余裕のあるうちに備えを決められない。**

これが作者の今回の指摘から置く仮説。金銭的な困窮や制度の利用制約をすべて事前準備で解決できる、とは仮定しない。

利用者は、予定入院について、病院の請求、生活上の支払い、給付金の入金を合わせた見通しがない人。診断や治療方針を決めるためには使わない。

## 利用者の体験

1. 利用者は「来月入院する。保険はあるけど、お金が足りるか分からない」のように話す。これまでの説明や手元のメモも、そのまま渡せる。
2. LLMが会話から事実・見込み・不明点を整理する。すでに話した条件を質問し直さない。医学的な予測や未確認の給付額を事実として作らない。
3. LLMが必要な比較を選ぶ。たとえば支払いと給付の順番が不明なら、給付が間に合う場合と遅れる場合を並べる。利用者が比較軸や入力項目を先に選べることを前提にしない。
4. 結果を大きく変える不明点があれば、その場で理由とともに聞く。分からなければ仮定の幅を示して試算を進め、実額が未確認であることを残す。定型の必須項目を埋め切るまで結果を出さない形にしない。
5. 試算は必要額の幅・不足が起きる時期・その差を生む条件を表示する。利用者は「もう1週間長引いたら」「給付が翌月だったら」と話して変えられる。
6. 会話に応じて、いま確認すると見通しが変わる相手・質問・時期を提案する。回答が届いたらそのまま伝えれば、LLMが条件を更新し再計算する。外部への連絡・提出の代行は別の範囲とする。

会話で準備を選ぶことと、実行の完了は分けて記録する。公開する試験データは架空のものだけにする。現時点ではLLM接続を実装していない。モデルに送る文脈・保存先・同意の扱いは、会話版の実装前に定める。

## 内部計算の確認用に作った架空例

以下の入力欄は計算エンジンを確かめるためのもので、利用者向けの操作仕様ではない。利用者にこの形式への転記を求めない。

- 対象期間: 2026-11-05〜2027-02-10。全収支を入力する家計簿ではなく、画面に示す入出金だけの比較。
- 入院費の支払日: 2026-11-16。70歳未満・協会けんぽ区分ウ・11月の1医療機関の入院・保険診療10割100万円・負担割合3割。多数回該当・年間上限到達・世帯合算なし。
- 窓口での保険診療分は上限未適用300,000円／適用92,940円。式は `85,800 + (1,000,000 − 286,000) × 1%`。[協会けんぽの適用期間別の表](https://www.kyoukaikenpo.or.jp/benefit/high_cost_medical_expenses/002/index.html)、確認2026-11-05。
- 対象外費用は30,000〜70,000円を初期値に置く。公表相場ではなく架空の見積もり幅。その他の支払い150,000円を11/30に置く。
- 民間給付は200,000円、12/9または12/23の入金を仮定できる。「入金なし」も選べる。給付の可否・金額・日付は保険契約から判定していない。
- 退院後の追加支払いは、12/10・1/10・2/10に各1回、合計0〜3回。1回10,000円を初期値に置く。受診・制度利用がその頻度になるという予測ではなく、本人が置く支払いの仮定。これに高額療養費を自動適用しない。
- 後日還付は日付未確認のため入金に算入しない。窓口負担の差を最終的な節約額にしない。
- 各イベント後の残高 = 手元資金 + それまでの入金 − それまでの支払い。同日の入出金は支払いを先に置く。不足する最大額 = `max(0, −期間中の最低残高)`。費用の下限・上限でそれぞれ計算する。表示する幅は確率的な信頼区間ではない。
- 入金前の不足を後日の給付で消さない。費用が幅の上限に寄った場合の、最初の不足日を表示する。余裕がある場合は「この入力範囲では不足なし」とする。
- 月をまたぐ入院、他の年齢・区分、税、休業給付、複数保険商品の判定は今回の試作の対象外。本実装へ進む際に範囲を決める。

## 頻度の扱い

制度やサービスを使う回数と、アプリを開く回数は別々に記録する。今回は前者の仮定を動かす。追加支払いの合計額と、期間中の不足する最大額の両方を示す。入金後に支払いが増える場合、合計費用は増えても入金前の不足額は同じことがある。

「どれくらい使いそうか」自体が分からない場合は、LLMがその不確かさを受け取り、複数の仮定で比べるか、対象と期間が合う公的な集団データを調べる。集団の平均をその人の回数と断定しない。個人の入院・再発・治療の確率は作らない。

## 検証の進め方

| 段階 | 観察すること | 分けて記録すること |
| --- | --- | --- |
| 使う前 | 必要額・入金時期・先に準備するものを既に説明できるか | 既に知っていたこと／不明なこと |
| 状況を話す | 利用者が整理し直さなくても、LLMが既知・不明を読み取れるか | 読み取れた条件／訂正が必要な条件 |
| 「分からない」と答える | 質問票を埋めさせず、仮定を明示して見通しを作れるか | 不明を維持できた／勝手に確定した |
| 「遅れたら」「回数が増えたら」と話す | 文脈を保って再計算し、生活上の影響を説明できるか | 条件の変化／判断の変化 |
| 次の準備を相談する | 誰に何をいつ確認するかが具体的になるか | 説明への納得／準備の意向 |
| 後で確認 | 実際の問い合わせ・書類の取得・申請が進んだか | 実行したこと／進まなかった理由 |

最初の検証は、架空の状況を普通の文章で伝えるところから始める。先に固定の質問や比較条件を教えない。結果は誘導せず、「不要だった」「窓口の説明で十分」「金額が分かっても動けない」も残す。

現段階の結果は未取得。作者が検証の優先順位を承認したことを、利用価値や支払意思の実証として数えない。
